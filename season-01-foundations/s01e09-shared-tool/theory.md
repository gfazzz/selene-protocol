# Теория — s01e09

## 1. Что делает `import`

`import scan` — не «подключить», а три шага:

1. **найти** модуль: посмотреть в `sys.modules`, а если там нет — пройти по
   каталогам из `sys.path`;
2. **выполнить** его код в новом пространстве имён, если он загружается впервые;
3. **привязать** имя в том модуле, который импортирует.

Второй шаг и есть причина всей серии. `def` при выполнении создаёт функцию и
привязывает к ней имя, `print` печатает, `open` открывает файл. Модуль — обычная
программа, и при импорте она работает от имени того, кто импортирует.

## 2. `sys.modules`: модуль загружается один раз

```python
>>> import sys, toolkit
>>> sys.modules["toolkit"] is toolkit
True
```

Второй `import toolkit` найдёт модуль в словаре и выполнять ничего не будет. Это
быстро и даёт важное свойство: у модуля одно состояние на программу. Все, кто
импортировал `toolkit.reading`, видят один и тот же объект модуля.

Из этого же следует неприятное: побочный эффект случается у того, кто импортировал
первым, и в том месте, где это случилось. Порядок импорта превращается в часть
поведения программы.

## 3. `sys.path`: где ищут модули

`sys.path` — обычный список каталогов. Первым идёт каталог запускаемого скрипта (или
текущий при `python -c` и `python -m`), дальше то, что задано в переменной
окружения `PYTHONPATH`, дальше стандартная библиотека и установленные пакеты.

Отсюда классическая ловушка: файл `random.py` в каталоге проекта перекрывает
стандартный модуль `random`. Имена модулей стоит выбирать так, чтобы они не
совпадали со стандартными.

Тест этой серии пользуется `PYTHONPATH`: он запускает отдельный процесс и
показывает ему, где лежит твой пакет.

## 4. Пакет и `__init__.py`

Каталог с `__init__.py` — обычный пакет. `import toolkit` выполняет этот файл, и
всё, что в нём определено, становится атрибутами пакета. Модуль `toolkit.scan`
после загрузки тоже становится атрибутом: `toolkit.scan`.

`__init__.py` — лицо пакета. Хороший `__init__.py` короткий: импорт публичного,
`__all__`, версия. Работа живёт в модулях.

Бывают и пакеты без `__init__.py` — «пакеты пространства имён» (PEP 420). Они нужны,
чтобы собрать один пакет из нескольких каталогов, и в этом курсе не встретятся.

## 5. Абсолютный и относительный импорт

```python
from toolkit.scan import first_gap   # абсолютный
from .scan import first_gap          # относительный: из того же пакета
```

Внутри пакета обычно пишут относительный: пакет можно переименовать или переложить,
и он не сломается. Относительный импорт работает только у модуля, который знает
свой пакет, — то есть загруженного через пакет. Запуск `python toolkit/scan.py`
этого знания не даёт, отсюда `ImportError`. `python -m toolkit.scan` — даёт.

## 6. Имена: `import` против `from … import`

`from toolkit.reading import read_node` привязывает **твоё** имя к тому же объекту:

```python
>>> import toolkit
>>> from toolkit.reading import read_node
>>> read_node is toolkit.reading.read_node
True
```

Это ссылка, как в s01e05. Переприсвоить своё имя можно, на модуль это не повлияет.
Обратное тоже верно: если кто-то переприсвоит `toolkit.reading.read_node`, твоё имя
продолжит указывать на старую функцию. Поэтому в коде, который должен видеть
изменения модуля, пишут `import toolkit.reading` и обращаются через точку.

## 7. Звёздочка и `__all__`

Без `__all__` звёздочка берёт все имена модуля, которые не начинаются с `_`. С
`__all__` — ровно перечисленные. На обычный `import` и на доступ через точку
`__all__` не влияет: `toolkit.walk.value_of` всё равно доступна, хотя в `__all__`
её нет, — просто это не обещание.

Подчёркивание в начале имени — соглашение, а не защита: «внутреннее, может
измениться». Python не запрещает к нему обращаться, но тот, кто обращается, берёт
риск на себя.

Звёздочку в рабочем коде обычно не пишут: читателю не видно, откуда взялось имя, а
два модуля могут молча перекрыть одно и то же имя. Удобна она в интерактивной
сессии и в `__init__.py`, который собирает пакет из модулей с собственными
`__all__`.

## 8. `__name__`, `__main__` и `python -m`

`__name__` — имя модуля. Для импортированного это полное имя (`"toolkit.scan"`), для
запущенного как программа — `"__main__"`. Проверка `if __name__ == "__main__":`
позволяет одному файлу быть и библиотекой, и программой.

`python -m toolkit` ищет пакет по `sys.path`, выполняет его `__init__.py`, потом
`__main__.py` под именем `"__main__"`. Так запускаются и стандартные инструменты:
`python -m venv`, `python -m pytest`, `python -m json.tool`.

## 9. Компромисс: удобство против обещания

Чем больше пакет отдаёт наружу, тем удобнее им пользоваться сегодня и тем труднее
менять его завтра. Каждое имя в `__all__` — обещание: убрать его — значит сломать
чей-то код. Поэтому в `__all__` идут функции, которыми пользуются, а служебные
функции вроде `_reporting` остаются с подчёркиванием.

Версия — вторая половина обещания. По ней пользователь пакета понимает, что
изменилось. Принято писать её строкой из трёх чисел (семантическое версионирование):
последнее растёт при исправлениях, среднее — при новых возможностях, первое — при
изменениях, которые ломают совместимость.

## 10. Циклический импорт

Если `alerts` импортирует `tally`, а `tally` — `alerts`, Python начнёт выполнять один
модуль, по дороге придёт ко второму, а тот попросит у первого имя, которое ещё не
определено. Результат — `ImportError` с упоминанием «partially initialized module».
Лечится не трюками, а устройством: общий код выносится в третий модуль.
