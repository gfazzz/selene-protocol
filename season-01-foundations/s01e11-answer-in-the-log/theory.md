# Теория — s01e11

## 1. Байты и текст

На диске нет букв. Там байты, и чтобы они стали строкой Python, их надо
**декодировать** по правилу — кодировке. Строка `str` хранит символы, `bytes` —
байты, и переход между ними всегда явный:

```python
>>> "кто".encode("utf-8")
b'\xd0\xba\xd1\x82\xd0\xbe'
>>> len("кто"), len("кто".encode("utf-8"))
(3, 6)
```

В UTF-8 латиница занимает байт, кириллица — два, многие другие символы — три или
четыре. Поэтому «размер файла в байтах» и «число символов» — разные числа, и
отрезать «первые сто байтов» журнала значит рискнуть разрезать букву пополам.

Текстовый режим `open` делает декодирование за тебя. Двоичный (`"rb"`) отдаёт байты
как есть — он понадобится, когда кодировка неизвестна заранее (S3).

> „стандартной кодировке“ и не говорит, в какой. Это объясняет половину архива».*

## 2. Откуда `open` берёт кодировку

Если `encoding` не указан, `open` берёт кодировку из настроек системы. На macOS и
большинстве Linux это UTF-8, в русской Windows исторически `cp1251`, в западной —
`cp1252`. Один и тот же код на одном и том же файле даёт разный текст.

Хуже всего то, что ошибки обычно нет. В `cp1251` почти у каждого байта есть своя
буква, поэтому байты UTF-8 чаще всего читаются без единой жалобы:

```python
>>> "кто".encode("utf-8").decode("cp1251")
'РєС‚Рѕ'
>>> "И".encode("utf-8")
b'\xd0\x98'
```

Исключение — байт `0x98`: в `cp1251` он не определён, а встречается в «И». Поэтому
журнал с «И» в `cp1251` падает, а журнал без неё молча становится кашей. Оба
журнала серии содержат «И», и на них чтение в `cp1251` падает.

`ascii` честнее: на первом же байте больше 127 он поднимает `UnicodeDecodeError`.
Тест серии запускает твою функцию именно так — в процессе, где кодировка по
умолчанию не UTF-8, — и смотрит, что получилось.

Python знает об этой ловушке. С версии 3.10 есть предупреждение `EncodingWarning`
(PEP 597): запусти `python -X warn_default_encoding`, и каждый `open` без
`encoding` о себе сообщит. PEP 686 делает UTF-8 кодировкой по умолчанию начиная с
Python 3.15. Курс требует 3.12, и даже на новых версиях явное `encoding="utf-8"`
остаётся лучшей привычкой: оно говорит читателю, в чём записан файл.

## 3. Перевод строки

Строки в файле разделены символом конца строки. В Unix это `'\n'`, в Windows —
пара `'\r\n'`, в старых Mac был `'\r'`. Текстовый режим по умолчанию приводит всё к
`'\n'` при чтении — это называется **универсальными переводами строк**. Параметр
`newline=""` отключает перевод, и тогда `'\r'` останется в строке: так читают CSV
(S3), где перевод строки может стоять внутри поля.

Строка, которую отдаёт цикл по файлу, кончается своим `'\n'`. Последняя строка
файла может его не иметь. Отсюда два правила:

- убирать ровно перевод строки: `line.rstrip("\n")`, а не «последний символ»;
- не считать, что `'\n'` есть всегда.

`line.strip()` убрал бы ещё и пробелы по краям. Для журнала это неважно, а для
данных, где пробел значим, — важно. Выбор зависит от формата, и его стоит делать
сознательно.

## 4. Почему `with`

Открытый файл держит ресурс системы. Его надо закрыть: иначе на больших обходах
кончатся дескрипторы, а записанное может остаться в буфере и не дойти до диска.

```python
log = open(path, encoding="utf-8")
lines = log.readlines()
log.close()      # не выполнится, если readlines упадёт
```

`with` гарантирует закрытие при любом выходе из блока: обычном, через `return` или
через исключение. Как он это делает — протокол контекстного менеджера, s02e09.
До тех пор достаточно правила: файл открывают только в `with`.

## 5. Построчно или целиком

| Способ | Память | Хвост |
|---|---|---|
| `for line in log` | одна строка за раз | `'\n'` в каждой строке, кроме, может быть, последней |
| `log.readlines()` | весь файл списком | то же |
| `log.read().split("\n")` | весь файл дважды | лишняя пустая строка в конце |
| `log.read().splitlines()` | весь файл дважды | без хвоста, но режет и по редким разделителям Unicode |

Для журнала смены разницы в памяти почти нет: сотни строк. Для архива за годы она
появится. Обход по строкам — правильная привычка с самого начала: он работает на
файле любого размера. Как устроена такая «ленивая» выдача, разберём в s02e07.

## 6. Находка, которая повторяется

Ответы SELENE Рейесу можно найти глазами. Такая находка не повторяется: никто не
знает, что пропущено, и на следующем журнале работу придётся делать заново.

Функция, написанная один раз, проходит сотню журналов одинаково. Её результат
может перепроверить любой: достаточно запустить. Поэтому тест серии не сверяет
ответ с константой, а **сажает** ответы в журналы, которые собирает сам с разными
зёрнами генератора, и требует найти ровно посаженное. Ответ, вписанный в код,
проходит один журнал из многих.

Это главный принцип всего курса, впервые проверенный в лоб. Финал курса — программа,
которая пересчитывает доказательство из исходных данных. Начинается он здесь.

## 7. Состояние в цикле

Чтобы распознать «пакет сразу после заметки», обход помнит одну вещь: была ли
предыдущая значимая строка заметкой и какой. Это имя обновляется **на каждой**
строке. Если обновлять его только на заметках, ответом станет любой пакет `0000`
после заметки, а не только следующая строка. Ошибка тихая: на журнале Рейеса она
может даже совпасть с правильным ответом.

Пустые строки в этот счёт не входят: `read_log` их уже отбросила. Это решение
формата, и оно записано в ТЗ, а не угадано.

## 8. Компромисс: ошибки декодирования

У `open` есть параметр `errors`. По умолчанию `"strict"` — на неверном байте
`UnicodeDecodeError`. `"replace"` подставит `'�'` и пойдёт дальше,
`"ignore"` молча выбросит байт. Для журнала, из которого достают доказательства,
годится только первое: испорченный ответ хуже упавшей функции. Мягкие режимы
понадобятся в S3, где выгрузка грязная заведомо и важно не остановиться, а
отбраковать.
