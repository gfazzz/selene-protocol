# Теория — s01e12

## 1. Откуда три выхода

Соглашение старше Python: оно пришло из Unix начала семидесятых. Каждый процесс
получает три открытых потока с номерами 0, 1 и 2 — ввод, вывод и вывод ошибок:

```python
>>> import sys
>>> sys.stdin.fileno(), sys.stdout.fileno(), sys.stderr.fileno()
(0, 1, 2)
```

Сначала потоков было два, и ошибки шли туда же, куда результат. Отдельный поток
для ошибок появился, когда вывод программ начали передавать друг другу через
`|`: сообщение об ошибке в середине данных ломало следующую программу, а человек
его не видел. С тех пор правило простое: **stdout — для данных, stderr — для
людей.**

Проверить это легко:

```
$ python3 -c "print('a'); import sys; print('b', file=sys.stderr)" > /dev/null
b
```

`> /dev/null` выбросил stdout, а stderr остался на экране.

## 2. Код возврата: одно число на всю работу

Когда процесс завершается, система запоминает одно число от 0 до 255. Больше
программа ничего не может сказать тому, кто её запустил, не открывая её вывод.

| Код | Значение по соглашению |
|---|---|
| 0 | успех |
| 1 | общая ошибка |
| 2 | неправильный вызов (так делают оболочка и `argparse`) |
| 64–78 | коды из `sysexits.h`: `EX_USAGE = 64`, `EX_NOINPUT = 66` и другие |
| 128 + N | процесс убит сигналом N |

`sysexits.h` доступен и из Python: `os.EX_USAGE`, `os.EX_NOINPUT` (только на
Unix). Курс держится простой тройки 0, 1, 2: её понимают все.

Число берётся по модулю 256, и это ловушка:

```
$ python3 -c "import sys; sys.exit(256)"; echo $?
0
$ python3 -c "import sys; sys.exit(-1)"; echo $?
255
```

Код 256 превращается в успех. Поэтому код возврата — не счётчик ошибок.

## 3. Все способы завершить программу

| Как | Код | Что напечатано |
|---|---|---|
| дошла до конца | 0 | — |
| `sys.exit()` или `sys.exit(None)` | 0 | — |
| `sys.exit(3)` | 3 | — |
| `sys.exit("сломалось")` | 1 | строка в stderr |
| `sys.exit(True)` | 1 | — (`True` — это 1, s01e01) |
| непойманное исключение | 1 | трассировка в stderr |

`sys.exit` не выключает процесс сразу, а поднимает `SystemExit`. Его можно
поймать, как любое исключение, — так `main` и превращает выход `argparse` в
код. Блоки `except Exception` его не ловят: `SystemExit` наследует не от
`Exception`, а от `BaseException`, ровно чтобы `except Exception` в чужом коде
не мешал программе завершиться.

```python
>>> issubclass(SystemExit, Exception), issubclass(SystemExit, BaseException)
(False, True)
```

## 4. Почему `main` возвращает, а не выходит

Устройство `def main(argv=None) → int` и одна строка
`raise SystemExit(main())` внизу модуля — распространённое соглашение. Оно даёт
три вещи сразу:

- **тестируемость.** Тест вызывает `main(["summary", "x.log"])` и получает число,
  без отдельного процесса;
- **повторное использование.** Другая программа может вызвать `main` и решить,
  что делать с кодом;
- **один выход.** Процесс завершается в одном месте, и его видно сразу.

`argv=None` вместо `argv=sys.argv[1:]` по умолчанию — та же история, что в
s01e08: значение по умолчанию вычисляется один раз, при определении функции.
`None` откладывает решение до вызова, а `parser.parse_args(None)` сам берёт
`sys.argv[1:]`.

## 5. `python -m` против пути к файлу

Есть два способа запустить модуль:

```
python3 toolkit/cli.py summary x.log      # как отдельный файл
python3 -m toolkit.cli summary x.log      # как модуль пакета
```

Первый не знает, что `cli.py` — часть пакета, и `from .errors import parse_all`
упадёт с `ImportError`: относительному импорту не от чего отсчитывать. Второй
импортирует пакет `toolkit`, а модуль `cli` выполняет с
`__name__ == "__main__"`. Для модулей внутри пакета правильный способ — `-m`
(s01e09).

## 6. Зачем `argparse`, если есть `sys.argv`

`sys.argv` — сырой список строк. Всё остальное приходится делать руками:
отличать флаг от значения, проверять число, писать справку, сообщать об
ошибке. В стандартной библиотеке было три поколения инструментов для этого:
`getopt` (по образцу функции из C), `optparse` и `argparse`. Последний умеет
подкоманды, позиционные аргументы, переменное число значений (`nargs="+"`) и
собирает справку из тех же описаний, по которым разбирает вызов.

Подкоманды — это способ дать одной программе несколько дел, как у `git commit`
и `git log`. У каждой подкоманды свой набор аргументов, а `dest="command"`
запоминает, какую выбрали.

Компромисс `argparse`: на ошибке он сам печатает и сам выходит. Для программы
это удобно, для функции — нет, отсюда перехват `SystemExit` в `main`.

## 7. Ничего лишнего в stdout

Программа, чей вывод читает другая программа, обязана выдавать результат
целиком или не выдавать вовсе. Половина ответов перед ошибкой хуже, чем ничего:
следующая программа не знает, что ответ неполный. Поэтому `main` сначала
собирает строки в список и печатает их, только если всё прочиталось.

Цена такого решения — память: весь результат лежит в списке до печати. Для
журналов смены это мелочь. Для потоков, которые не помещаются в память, нужен
другой приём — генераторы (s02e07) и запись во временный файл.

## 8. Как запускает расписание

Расписание (`cron`, CI, ночной прогон) запускает команду без человека рядом.
Всё, что оно знает о результате, — код возврата. На нём держатся и оболочка
(`команда && следующая` выполнит вторую, только если первая вернула 0), и
`make` (остановится на первой команде с ненулевым кодом).

Отсюда правило: **каждый путь программы кончается осознанным кодом.** Успех —
0. Известная беда — свой ненулевой код и строка в stderr. Неизвестная беда —
трассировка и 1: здесь Python сделает правильно сам.
