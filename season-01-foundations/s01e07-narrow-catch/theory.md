# Теория — s01e07

## 1. Откуда исключения

В C из соседнего курса функция сообщает об ошибке возвращаемым значением:
`-1`, `NULL`, код в `errno`. Вызывающий обязан проверить его каждый раз, и если
забыл — программа идёт дальше с мусором. Исключения переворачивают умолчание:
ошибка прерывает работу сама, и чтобы продолжить, её надо поймать явно. Забыть
поймать можно, но тогда программа остановится, а не соврёт.

Скрипт Рейеса нашёл способ вернуть худшее из старого мира: `except: pass`
превращает исключение обратно в молчаливое возвращаемое значение, только без
значения.

> *SELENE, в отладочном канале: «Самый надёжный способ не получать плохих новостей
> известен давно. Им пользуются и в управлении колонии».*

## 2. Полная форма `try`

```python
try:
    number = float(field)
except ValueError as err:
    print("плохое поле:", err)
else:
    print("разобрано:", number)
finally:
    print("готово")
```

`else` выполняется, если ошибки не было. В него кладут код, ошибки которого
ловить не надо: так `try` остаётся узким. `finally` выполняется всегда, даже при
`return` и непойманной ошибке. Для закрытия ресурсов есть более удобная форма —
`with`, к ней вернёмся в s02e05.

Одно `except` может перечислить несколько классов кортежем:
`except (ValueError, TypeError):`. Порядок нескольких `except` важен: первым
сработает первый подходящий, поэтому частные классы пишут выше общих.

## 3. Иерархия встроенных исключений

```
BaseException
├── KeyboardInterrupt, SystemExit, GeneratorExit
└── Exception
    ├── ValueError
    ├── TypeError
    ├── AttributeError
    ├── LookupError
    │   ├── KeyError
    │   └── IndexError
    └── ...
```

Наверху стоят исключения, которые означают «остановись»: `Ctrl+C` и выход
программы. Они нарочно не потомки `Exception`, чтобы `except Exception:` их не
ловил. Голый `except:` ловит и их, поэтому цикл с ним иногда не остановить.

`ValueError` — правильный тип, но неверное значение: `float("9,6")`.
`TypeError` — неправильный тип: `"118" + 1`. `AttributeError` — у объекта нет
такого атрибута: `None.split(";")`. Различать их полезно: первое обычно означает
плохие данные, второе и третье — ошибку в коде.

```python
>>> None.split(";")
AttributeError: 'NoneType' object has no attribute 'split'
```

## 4. Зачем своя иерархия

Можно было бы поднимать `ValueError` с хорошим сообщением. Но тогда `except
ValueError` у вызывающего поймает и плохой пакет, и любую другую `ValueError`
изнутри, например из чужой библиотеки. Свой класс даёт адрес: эта ошибка пришла
отсюда и значит именно это.

Обычная схема для библиотеки — один общий предок и несколько частных классов:

```python
class TelemetryError(Exception): ...
class BadPacket(TelemetryError): ...
class StaleNode(TelemetryError): ...      # пример на будущее
```

Вызывающий выбирает точность: `except BadPacket` для одного случая, `except
TelemetryError` для всех ошибок библиотеки сразу. Так устроены и большие
библиотеки: у `requests` есть `RequestException`, у `sqlite3` — `sqlite3.Error`.

Унаследовать `BadPacket` и от `ValueError` можно, и иногда так делают ради
совместимости. Цена — `except ValueError` снова ловит всё подряд. В этой серии
`BadPacket` не потомок `ValueError` намеренно.

## 5. Атрибуты ошибки

Исключение — обычный объект, и у него могут быть поля:

```python
>>> err = BadPacket("поле value: '9,6' — не число", field="value")
>>> err.field
'value'
>>> str(err)
"поле value: '9,6' — не число"
```

Атрибут нужен программе: сосчитать отклонённые по полям, выбрать реакцию. Текст
нужен человеку. Разбирать текст сообщения программой — хрупко: его поменяют при
переводе на другой язык, и подсчёт сломается без единой ошибки.

С Python 3.11 к любой ошибке можно добавить заметку, не меняя класс:

```python
>>> e = ValueError("x")
>>> e.add_note("строка 4")
>>> e.__notes__
['строка 4']
```

Заметки печатаются в трассировке. Это удобно, когда ошибку поднял не ты, а
подробности знаешь ты.

В сообщении значение поля стоит как `{value!r}`: `!r` в f-строке подставляет
`repr` значения, с кавычками. Поэтому `'9,6'` видно как строку, а пустое поле не
пропадает из сообщения, а выглядит как `''`.

## 6. Причина и контекст

При ошибке внутри `except` Python связывает новую ошибку со старой двумя
способами:

| Как поднята | `__cause__` | `__context__` | Что пишет трассировка |
|---|---|---|---|
| `raise New() from err` | `err` | `err` | «…was the direct cause of…» |
| `raise New()` | `None` | `err` | «During handling of the above exception, another exception occurred» |
| `raise New() from None` | `None` | `err`, но скрыт | только новая |

Вторая строка выглядит как две аварии подряд: «пока разбирались с первой,
случилась вторая». Если вторая — сознательный перевод первой на язык библиотеки,
это надо сказать явно: `from err`.

`from None` уместен, когда причина — деталь реализации и только запутает
читателя. Здесь причина полезна: исходный `ValueError` говорит, что именно
не понравилось `float`.

## 7. Где ловить

Ловить ошибку стоит там, где известно, что с ней делать. Это не обязательно там,
где она возникла:

- `parse_strict` знает, какое поле плохое, но не знает, что делать с плохим
  пакетом: выбросить, отложить, остановить смену. Поэтому она поднимает ошибку.
- `parse_all` знает: плохой пакет — в отклонённые, разбор продолжается. Поэтому
  ловит она.
- Что делать с `None` вместо строки, не знает никто из них. Пусть решает тот, кто
  этот `None` передал.

Этот принцип называют по-разному; суть одна — не ловить «на всякий случай».

## 8. Сначала проверить или сначала попробовать

Есть два стиля. «Посмотри, прежде чем прыгать»: сначала проверить, что строка
похожа на число, потом превращать. «Проще попросить прощения»: превратить и
поймать ошибку. В Python обычно выбирают второй: проверка до действия часто
неполна (`"1e3"`, `"nan"`, `"1_000"` — всё числа) и повторяет работу самой
функции. Флаг тревоги — исключение из правила: допустимых значений два, и
проверить их проще, чем ждать ошибки, которой не будет.

## 9. Компромисс: остановить или отложить

`parse_all` выбрала «отложить»: плохие строки собираются, поток идёт дальше.
Для телеметрии это правильно: одна плохая строка не должна прятать тысячу
хороших. Для расчёта денег правильно обратное, и об этом будет S5. Важно не
какой выбор, а то, что он сделан явно: отклонённые возвращаются, их видно, их
можно сосчитать. Рейес тоже откладывал, только в никуда.
