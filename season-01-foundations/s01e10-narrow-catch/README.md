## Чему ты научишься

- Читать исключение: тип, сообщение и трассировку, — и понимать, где оно возникло.
- Ловить **узко**: ровно ту ошибку, с которой знаешь, что делать.
- Заводить **свою иерархию** ошибок, чтобы вызывающий мог поймать их все и
  только их.
- Приёму, который дороже синтаксиса: **ошибка — это новость, а не помеха.**
  Её передают дальше с подробностями, а не прячут.

## Теория: исключения и своя иерархия

### Исключение — это значение

Когда операция не может выполниться, Python создаёт объект-исключение и
прекращает обычный ход программы:

```python
>>> float("9,6")
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
ValueError: could not convert string to float: '9,6'
```

Последняя строка — тип и сообщение. Выше — трассировка: путь вызовов от места,
где ошибка возникла, до места, где её никто не поймал. Читают её снизу вверх.

Поймать исключение можно конструкцией `try` / `except`:

```python
>>> try:
...     value = float("9,6")
... except ValueError as err:
...     print("плохое показание:", err)
...
плохое показание: could not convert string to float: '9,6'
```

### Ловить узко

У исключений есть иерархия: `ValueError` — частный случай `Exception`, а
`Exception` — частный случай `BaseException`. `except` ловит указанный класс и
всех его потомков. Поэтому чем выше класс, тем больше попадает в сеть:

```python
>>> ValueError.__mro__
(<class 'ValueError'>, <class 'Exception'>, <class 'BaseException'>, <class 'object'>)
>>> KeyboardInterrupt.__mro__
(<class 'KeyboardInterrupt'>, <class 'BaseException'>, <class 'object'>)
```

Голый `except:` ловит вообще всё, включая `KeyboardInterrupt` от `Ctrl+C` и
выход программы. `except Exception:` честнее, но ловит и опечатку в имени
переменной, и `None` вместо строки. Ни то ни другое не отличает плохие данные от
ошибки в коде.

Правило простое: **ловят то, с чем знают, что делать.** Разбор пакета знает,
что делать с плохим числом в поле. Что делать с `None` вместо строки, он не
знает: это ошибка того, кто его вызвал, и она должна до него дойти.

### Своя иерархия

Чтобы вызывающий мог поймать «все ошибки телеметрии и только их», им нужен общий
предок:

```python
class TelemetryError(Exception):
    """Общий предок ошибок телеметрии."""

class BadPacket(TelemetryError):
    ...
```

`class` здесь — приём записи, устройство классов разберём в s02e03. Важно одно:
`except TelemetryError` поймает `BadPacket`, но не поймает `AttributeError` от
`None`. Сеть ровно того размера, что нужен.

У ошибки могут быть атрибуты. `err.field == "value"` говорит программе, какое
поле плохое, а сообщение говорит то же человеку. Нужно и то и другое.

### `raise … from`: не терять причину

Своя ошибка часто возникает из чужой. Если поднять её внутри `except`, причину
стоит сохранить явно:

```python
try:
    number = float(value)
except ValueError as err:
    raise BadPacket(f"поле value: {value!r} — не число", field="value") from err
```

`from err` кладёт исходную ошибку в `__cause__` новой, и трассировка покажет
обе с пометкой *«The above exception was the direct cause of the following
exception»*. Без `from` Python тоже запомнит предыдущую ошибку, но как
случайный контекст, а не как причину. `from None` прячет её совсем, и иногда
это правильно. Сегодня — нет.

## Проверка: SELENE задаёт вопросы

```
[КАНАЛ 0 · УЗЕЛ НЕ УКАЗАН]
ТРИ ВОПРОСА. НА КАЖДЫЙ ЕСТЬ ОТВЕТ ЛУЧШЕ, ЧЕМ PASS.
```

**1.** «Чем `except:` хуже, чем `except Exception:`, и чем оба хуже твоего?»

<details><summary>Ответ</summary>

Голый `except:` ловит и `KeyboardInterrupt`, и выход программы: такой цикл
нельзя даже остановить. `except Exception:` их пропускает, но ловит ошибки в
коде: `None` вместо строки, опечатку в имени. `except TelemetryError:` ловит
только то, что разбор сам назвал плохими данными.
</details>

**2.** «Зачем `BadPacket` хранить поле, если в сообщении и так написано?»

<details><summary>Ответ</summary>

Сообщение — для человека, атрибут — для программы. Сводке Окафор надо посчитать,
сколько строк отклонено по полю `value`, а разбирать для этого текст сообщения —
та же ошибка, что и судить о значении по виду в s01e01.
</details>

**3.** «`raise BadPacket(...)` внутри `except ValueError` без `from`. Что потеряно?»

<details><summary>Ответ</summary>

Причина. В `__context__` старая ошибка останется, но `__cause__` будет `None`, и
по трассировке не понять, было ли это следствием или второй аварией во время
обработки первой.
</details>

## Разбор типичных ошибок

1. **`except: pass`.** Ошибка Рейеса. Плохая строка исчезает, хорошие этого не
   замечают, отчёт выглядит полным.
2. **`except Exception` в `parse_all`.** `None` вместо строки уходит в
   отклонённые как «плохой пакет», и ошибку вызывающего кода никто не увидит.
3. **`except ValueError` в `parse_all`.** `BadPacket` не потомок `ValueError`,
   поэтому первая же плохая строка роняет весь поток.
4. **`raise` без `from err`.** Причина остаётся только случайным контекстом.
5. **Номер строки с нуля.** Строки считают с единицы: «строка 0» — не туда.
6. **Флаг без проверки.** `"2"` молча превращается в «нет тревоги», ровно как
   `bool("0")` в s01e01, только наоборот.
